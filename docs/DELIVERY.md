# 消息与提醒设计

## v33 · 2026-10-16

用户应当一眼分清：事情有进展、现在需要我决定、时间到了要去做什么。消息只讲重点，完整上下文放在任务详情。

| 发生什么 | 用户看到什么 | 实现边界 |
|---|---|---|
| App 内有任务进展 | 单条短回复＋静态任务回执 | 工作台或详情中用短暂通知条提供入口，不抢当前阅读位置 |
| 离开后返回 | 一句重点摘要＋一张汇总卡 | 同 task_id 取最新状态；中间事件保留，重复进入不重复汇总 |
| 主动问全部任务 | 用户提问＋摘要＋同款汇总卡 | 任务主体去重，需协助先展示，前三项可见，其余展开 |
| 到提醒时间 | 独立的待办提醒 | 时间、事项、物品清单、知晓或稍后提醒；不是任务状态回执 |

用户米色气泡为右侧发言。任务回执是左侧白色结构卡，完成浅绿、需协助浅蓝，常规默认白色，中断同灰色，轻量边线辅助识别。汇总是白色列表，不嵌套一组完整任务卡。提醒为铃铛＋醒目时间＋浅琥珀通知区，不显示“已完成”任务状态。

## 游泳用例

演示固定今天为 2026-10-15，初始 18:45。用户提出今晚 20:00 游泳、提前半小时提醒。

1. 18:45：回复“已为您创建提醒”。任务“提醒今晚游泳”状态已完成，代表设置成功。通知计划等待 19:30，活动实例是 20:00 待启动、需本人在场。
2. 19:30：发独立提醒“该准备去游泳了”，突出 20:00、剩余 30 分钟，带上泳衣／泳帽／泳镜／毛巾／水。
3. 点知道了：记录知晓，不更改实际活动完成状态。点 10 分钟后再提醒：19:40 产生另一次通知，旧通知显示已改为 19:40。
4. 离开时到点：普通进展统一汇总，到点提醒单独补呈；若回来已经过 20:00，说明原定时间已过。
5. 取消后续提醒：停止通知，不代表取消去游泳。20:00 后是否到场仍由用户确认。

今晚明确的 20:00 安排替代内置“每日 19:00 游泳”样例的当天实例，避免当天重复冲突；其他日期的周期样例保留。完成提醒设置后不把主体直接归档，安排仍能找到并取消。

## 数据与交互

- `S.delivery.queue`：隐藏／离开期间的事件。返回后一次消费，汇总保留源事件。
- `S.reminders`：通知时间、活动时间、版本、已触发通知实例、知晓、取消。
- 设置任务：独立 `done` 主体，静态设置回执不可被后续提醒改写。
- 到场实例：20:00 的子实例，待启动／需本人确认／用户明确完成，不能由通知知晓推导完成。
- `visibilitychange`、`pagehide`、`pageshow`：共用同一离开／返回流程。内部切页不属于离开。
- 提醒识别暂支持指定示例；其他时间表达明确提示演示范围。

任务详情增加左滑关闭，保留原关闭按钮。只响应明显水平向左单指动作，排除垂直滚动、多指和输入编辑。关闭后抑制残留点击，避免切底层页。

## 验证与未接入项

运行 `node tests/conversation.cjs` 和 `node tests/delivery.cjs`。状态与生命周期在模拟 DOM 中检查，未做浏览器视觉／真机手势验收。此版本没有系统 Push、真实语音、服务器调度或网页关闭期间的持续执行；固定时钟和按钮只用于复现演示，不应被描述为生产能力。
